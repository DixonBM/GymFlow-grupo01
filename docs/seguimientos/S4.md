## 2. Instalación desde cero

La instalación independiente del [issue #15](https://github.com/DixonBM/GymFlow-grupo01/issues/15) está **pendiente de ejecución y evidencia**. Dixon Bustos coordina la prueba con una persona que pueda seguir únicamente el [README](../../README.md) en un entorno limpio.

La prueba debe registrar quién la ejecutó, la fecha, el entorno y el commit. Incluye iniciar los contenedores, cargar los datos de prueba, verificar MongoDB y Redis, iniciar sesión y recorrer el flujo de socio, membresía y pago. Las capturas y los resultados se incorporarán en `docs/evidencias/S4/`.

La revisión documental encontró que el README todavía ubica las máquinas fuera del MVP y describe una etapa anterior del proyecto. La actualización corresponde al [issue #16](https://github.com/DixonBM/GymFlow-grupo01/issues/16), asignado a Dixon Bustos.

## 3. Redis y MongoDB

| Clave Redis | Tipo y contenido | Vigencia | Invalidación |
| --- | --- | --- | --- |
| `gymflow:s1:dashboard:<gimnasioId>` | String JSON con el resumen del tablero de un gimnasio. | 60 segundos por defecto. La variable `CACHE_TTL_SECONDS` permite configurarla entre 1 y 3600 segundos. | `DEL` sobre la clave del gimnasio tras confirmar una escritura que afecta el resumen. |

[ReportCache.php](../../src/ReportCache.php) usa `GET` para leer, `SETEX` para guardar con vencimiento y `PING` para verificar la conexión. La invalidación actúa sobre una clave específica. Cuando la caché está indisponible, el tablero consulta MongoDB, como se documentó en [S3](S3.md#3-conexión-y-recuperación-de-redis).

El repositorio cuenta con [setup.php](../../scripts/setup.php) para cargar datos sintéticos mediante PHP. El script de carga mediante `mongosh` solicitado para S4 queda pendiente. La URI de MongoDB del entorno se configura de forma privada y el repositorio incluye valores de ejemplo en [`.env.example`](../../.env.example).
