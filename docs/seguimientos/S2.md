## 1. Objetivo

Comprobar el funcionamiento del flujo principal de GymFlow:
administrar gimnasios, registrar socios, crear planes, asignar
membresías y registrar pagos, conservando los datos en MongoDB.

## 2. Trabajo realizado

Se realizaron pruebas manuales desde la aplicación publicada en
el servidor universitario y se organizaron sus evidencias en
docs/evidencias/S2/.

| Actividad | Resultado |
| --- | --- |
| Registro de gimnasio | El nuevo gimnasio apareció en el listado. |
| Registro de administrador | Se creó una cuenta administrativa asociada al nuevo gimnasio. |
| Registro de socio | El socio se guardó y apareció en el listado. |
| Edición de socio | Los cambios se guardaron sin duplicar el registro. |
| Creación de plan | Se guardaron el nombre, la duración y el precio. |
| Edición del precio | Se actualizó el monto sin duplicar el plan. |
| Consulta de membresía | Se mostraron el período, precio contratado y estado. |
| Cancelación de membresía | Se conservó el registro con estado Cancelada. |
| Creación de nueva membresía | Se registró un nuevo período con sus condiciones. |
| Registro de pago manual | El pago quedó asociado a la membresía. |
| Anulación de pago | Se conservó el movimiento con su estado y motivo de anulación. |
| Persistencia | Los datos continuaron disponibles después de salir y volver a ingresar, según la comprobación manual reportada. |

No se reportaron errores durante estas operaciones normales.
Los pagos son registros manuales; GymFlow no realiza transferencias
bancarias.

El detalle de las pruebas está disponible en
[PRUEBAS-S2.md](../PRUEBAS-S2.md).

## 4. Estado de MongoDB y Redis

MongoDB Atlas almacena los datos de gimnasios, usuarios, socios,
planes, membresías y pagos.

Redis está disponible y la documentación del proyecto registra
pruebas satisfactorias de conexión y caché MISS → HIT, con un
tiempo de vida de 60 segundos.

Estas comprobaciones demuestran conectividad y uso de la caché;
no constituyen una medición de rendimiento ni una prueba completa
de recuperación ante fallos.

**Evidencia:** [Verificación de Virtualmin, MongoDB y Redis](../evidencias/S1/15-verificacion-final-virtualmin-atlas-redis.png).

**Antecedentes:** [Bitácora S1](S1.md).

## 6. Decisiones técnicas

- Mantener MongoDB como fuente definitiva de los datos.
- Utilizar Redis como caché temporal del dashboard por gimnasio.
- Conservar el historial de membresías canceladas y pagos anulados.
- Mantener las condiciones contratadas de las membresías aunque
  cambie posteriormente el precio del plan.
- Organizar las evidencias por seguimiento.
- Trasladar la medición de rendimiento al Seguimiento 3.

## 7. Pendientes y justificación

### Medición de rendimiento: reprogramada para S3

Queda pendiente ejecutar y documentar la comparación de tiempos
con y sin caché Redis.

Aunque el repositorio incluye cache-benchmark.php, no se dispone
de resultados de ejecución para incorporarlos a esta entrega.
Se reprograma esta actividad para S3, donde se ampliará la medición
a tres operaciones representativas, con al menos tres ejecuciones
por operación y reporte de la mediana.

Antes de utilizar el resultado del script se revisará el cálculo
de mediana para muestras con un número par de ejecuciones.

### Consolidación de pruebas adicionales

El documento PRUEBAS-S2.md mantiene casos pendientes relacionados
con datos inválidos, duplicados, acceso entre gimnasios,
invalidación de caché y fallos de conexión.

Se revisarán los resultados disponibles con el equipo y se
incorporarán sus evidencias. Los casos sin resultados documentados
no se presentan en esta bitácora como pruebas aprobadas.

### Cierre documental de S2

Queda pendiente publicar esta bitácora y crear el tag v0.2.0 sobre
el commit seleccionado para la entrega.
